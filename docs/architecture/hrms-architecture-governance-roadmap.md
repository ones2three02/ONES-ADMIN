# ONES-ADMIN HRMS 架构治理路线图

更新时间：2026-07-07  
当前版本：v0.0.144
定位：长期架构治理基线，不替代具体需求设计、数据库迁移说明或接口文档。

## 1. 目标

ONES-ADMIN 的长期目标不是做一个只满足演示的后台模板，而是建设一个企业级、生产可用、可持续演进的 HRMS 管理平台。后续每个版本都应优先考虑整体架构质量，而不是只完成单点页面或接口。

本路线图用于约束后续决策：

- 前端、后端、数据库、接口、安全、权限、工程化、部署和可观测性必须一起评估。
- HRMS 是主业务域，系统基础模块服务于 HRMS，而不是让 HRMS 迁就模板代码。
- 优秀开源项目只作为设计输入，不直接复制其技术栈、视觉或复杂度。
- 每个小版本都应有明确目的、验证证据和可回滚边界。

## 3. 当前基线

截至 v0.0.144，ONES-ADMIN 已形成以下基础：

- 前端基线：Vben / Ant Design Vue / VxeGrid / Pinia / Vue Router，已有登录页、系统管理、接口管理、审计日志、文件管理、HRMS 员工/合同/花名册/概览等页面，并在 v0.0.144 沉淀前端引导式交互治理规范。
- 后端基线：Spring Boot 3.5、Java 21、Sa-Token、MyBatis-Plus、Flyway、统一异常、TraceId、操作审计、防重复提交、接口资源治理。
- 数据基线：`sys_` 系统域和 `hr_` HRMS 域已分离，迁移脚本已纳入 Flyway 和 CI 数据库迁移报告。
- 权限基线：菜单、按钮权限、角色数据范围、HRMS 员工读接口数据范围、敏感字段脱敏已落地第一阶段。
- 工程基线：Jenkins 验证门禁、本地统一验证入口、版本一致性、仓库扫描、构建元数据、环境配置报告、数据库迁移报告、前端布局报告、接口治理报告、验证摘要和发布证据包已建立。
- HRMS 基线：员工主数据、组织关系、任职记录、资料附件、生命周期、合同、合同附件、花名册导入导出、人力概览、员工档案和预警运营已有一期闭环。

## 4. 架构原则

### 4.1 模块化单体优先

当前阶段保持模块化单体，不急于拆微服务。拆分条件必须同时满足：

- HRMS 业务边界稳定；
- 数据归属和事务边界清晰；
- 接口契约、事件契约和鉴权策略已经治理；
- Jenkins 已能分别验证服务边界；
- 运行时监控、日志追踪、发布回滚具备支撑。

### 4.2 HRMS 业务域优先

系统基础能力继续服务 HRMS 主线。短期优先顺序：

1. 员工主数据和员工档案中心继续增强。
2. 组织、岗位、职级、数据范围和字段权限持续收敛。
3. 假勤、审批、薪资、绩效等复杂域只在主数据和流程基座稳定后推进。
4. 任何 HRMS 写入必须保留审计、TraceId、权限码、数据范围和迁移证据。

### 4.3 安全默认

安全能力不以后补为前提。后续新增模块默认满足：

- 登录失败限制、账号锁定、Token 过期和多端策略可配置；
- 所有敏感字段有脱敏、授权查看和审计记录；
- 所有文件访问经过业务归属授权；
- 所有批量导入有批次、错误明细和可追踪来源；
- 所有外部回调和第三方登录不在前端暴露 Secret。

### 4.4 前端风格一致

新增前端页面默认遵循：

- 复用 Vben 页面布局、查询表单、VxeGrid、抽屉、弹窗和按钮权限模式。
- 高密度业务页优先信息组织，不做营销式大卡片和过度装饰。
- 图标、空状态、状态标签和主操作都应服务用户任务，不堆解释文案。
- 列表页必须保持稳定高度和横向滚动边界，不允许因筛选、空状态、提示条导致表格持续变小。

### 4.5 治理证据优先

架构治理必须有机器可读或文档可追溯证据：

- 版本号进入 `VERSION`、README、后端默认配置、OpenAPI、接口治理报告和测试断言。
- 数据库变更进入 Flyway、迁移治理报告和回滚说明。
- 接口变更进入接口资源治理、Manifest、权限码、风险等级和审计策略。
- 前端布局和工程化变更进入单测、类型检查、构建或专项报告。

## 5. 目标架构地图

| 领域 | 目标状态 | 近期治理动作 |
| --- | --- | --- |
| 前端工程化 | Vben 风格统一、业务组件可复用、表格/表单体验稳定、页面类型契约清晰 | 沉淀 HRMS 页面模板、列表/详情/档案组件规范、继续减少硬编码和重复样式 |
| 后端工程化 | 模块边界清晰，Controller 轻量，Service 承载业务和事务，Mapper 只做数据访问 | 将 HRMS 大 service 逐步按子域拆分为 employee、contract、document、roster、overview 等服务 |
| 数据库治理 | Flyway 版本连续、字段默认值和索引有依据、破坏性 SQL 需审批 | 为后续请假/考勤/薪酬域先设计边界，不提前建过度宽表 |
| 权限与安全 | RBAC + 数据范围 + 字段级授权 + 文件授权 + 审计闭环 | 扩展数据范围到更多 HRMS 读写接口，补字段级权限策略文档和测试 |
| API 治理 | 所有接口有 owner、权限、风险、生命周期、审计和发布门禁 | 把治理动作项继续作为 Jenkins 和接口管理页的共同输入 |
| 可观测性 | TraceId、操作日志、异常日志、健康检查和发布证据可关联 | 增加关键业务指标、登录失败指标、导入失败率、文件访问异常指标 |
| CI/CD | 本地与 Jenkins 同源验证，构建证据可审计，后续部署可干跑 | 部署前先引入环境矩阵、配置检查和数据库迁移 dry-run |
| HRMS 业务 | 员工档案中心 + 流程 + 合规留痕，逐步扩展假勤薪酬绩效 | 先做组织/员工/合同/资料深度治理，再推进请假和审批流 |

## 6. 三阶段路线

### 阶段 A：企业级基座收敛

目标：让当前一期能力变得稳定、可维护、可审计。

- HRMS 后端按子域拆分 service，避免一个服务承载过多职责。
- 系统参数、岗位/职级/字典和文件策略进一步纳入配置治理。
- 登录安全、SSO 适配、数据范围和字段脱敏形成可配置策略。
- 前端沉淀 HRMS 页面模板，保证列表、档案、预警、导入页面体验一致。
- CI 报告继续覆盖版本、环境、数据库、接口、前端布局和发布证据。

### 阶段 B：流程化 HRMS

目标：从主数据维护升级到 HR 业务流程管理。

- 引入请假、审批、假期余额、考勤异常等流程域。
- 将审批流作为可插拔能力接入 HRMS，不把流程逻辑写死在单个 Controller。
- 建立流程事件、业务状态机、操作审计和消息通知的统一模式。
- 前端增加待办、审批、流程详情和异常处理视图，继续沿用 Vben 后台风格。

### 阶段 C：平台化与可扩展

目标：在业务稳定后推进平台能力，而不是提前复杂化。

- 代码生成只生成低风险 CRUD 骨架，业务规则必须人工审查。
- 多租户、组织隔离、字段级权限、合规归档和审计报表成熟后再考虑服务拆分。
- 企业微信、钉钉、飞书等第三方接入统一认证适配层。
- 报表、薪资、绩效等高敏模块先做权限、脱敏、审计和数据模型评审，再实现功能。

## 8. 决策记录

| 决策 | 结论 |
| --- | --- |
| 是否立即拆微服务 | 不拆。继续模块化单体，等业务边界、CI、监控和部署能力成熟后再评估。 |
| 是否直接引入低代码 | 不直接引入。先吸收元数据和代码生成思路，限定在低风险 CRUD 骨架。 |
| 是否另做 HR SaaS 风格前端 | 不做。继续保持 Vben / Ant Design Vue 企业后台风格。 |
| 是否优先做薪资 | 暂不优先。薪资涉及高敏数据、地区合规、权限和审计，必须在字段权限和流程基座稳定后推进。 |
| 是否将飞书作为主要三方入口 | 是。登录页飞书优先，后端需补 OAuth 回调、账号绑定、审计和 Sa-Token 签发闭环。 |

## 9. 后续维护规则

- 每个新增业务模块都要在本路线图或对应业务设计文档中说明模块边界。
- 每次引入开源项目设计思想时，必须记录“吸收点”和“不直接照搬点”。
- 每个小版本完成后更新 CHANGELOG，并确认是否需要同步本路线图的近期 backlog。
- 涉及数据库、认证、权限、文件、审计、部署的变更必须补充风险和回滚说明。
